Case Study 02 · Design Systems

One design language for an enterprise procurement platform.

Establishing a shared design language across product, marketing, and client-facing surfaces

Product
EffiGO eProcurement
My Role
Lead Designer
Scope
Foundations + Component Library
01 — Context

No system, no shared language

EffiGO is an enterprise eProcurement platform serving clients across sourcing, procurement, dispatch, and contract management. As the product grew across modules, so did the inconsistency — each area developed its own visual patterns, component styles, and interaction logic independently.

The problem wasn't isolated to the product. Marketing materials, client presentations, and the platform itself all looked like they came from different companies. There was no brand system, no shared component set, and no common language between designers and developers.

I helped design the system from the ground up — establishing foundations, designing the component library, and working directly with the development team through handoff.

02 — The Problem

One product, no shared visual logic

Every team was making design decisions independently, with no reference point. Each module used its own layout logic, spacing rules, and component styles, so dashboards, tables, and configuration-heavy forms all behaved differently — and users had to relearn the interface each time they moved between modules.

Complex admin and workflow screens became dense and hard to scan because no hierarchy principles were applied consistently. Beyond the product, marketing decks and client presentations looked disconnected from what clients actually used day to day.

The development cost
Without a shared component library, the same UI patterns were being rebuilt from scratch across modules — time spent on solved problems rather than new ones.
03 — The System

Principles first, then foundations, then every component on top

Each layer inherits from the one above it, so a decision made once in the foundations shows up consistently across every module.

04 — Impact

From scattered patterns to a shared framework

What began as inconsistency across every surface became a framework that simplified decisions and reduced friction — for designers, developers, and clients alike.

05 — Approach

Principles before pixels

Before building a single component, I established the principles that would govern every decision. For a data-heavy enterprise product, components had to work across dense admin tables and sparse empty states, across tight and wide viewports, and for both technical and non-technical users.

The sequencing was deliberate: foundations first — colour, typography, spacing — then components. Without a stable foundation, every component decision becomes a negotiation. With it, components almost design themselves.

Principle 01
Clarity over decoration
Every visual decision had to earn its place by aiding comprehension. Nothing decorative that didn't carry meaning.
Principle 02
Density without noise
Enterprise workflows require dense UIs. The system had to support high information density without creating visual chaos — structure through hierarchy, not decoration.
Principle 03
Predictable patterns
Users moving between modules should never have to relearn how something works. Consistency reduces cognitive load across the whole product.
Principle 04
Built for handoff
Every component needed to be documented well enough that a developer could implement it without a design walkthrough. The system had to work without me in the room.
06 — Foundations

A shared language for the whole product

Foundations are the decisions that everything else inherits from. Getting these right meant every component built on top of them would feel consistent — without anyone having to consciously enforce it.

Colour

A primary navy anchors the brand across product and marketing. A semantic status layer gives meaning to state across every module — including a distinct colour for rejection. In a procurement workflow, the difference between a warning and a rejection carries real business consequence, and the colour system had to reflect that.

Semantic roles shown with neutral example tones, not the product's actual palette.

Typography — Manrope + Poppins

Two typefaces, each with a clear role. Manrope Extrabold handles headings and module titles, bringing structural weight to dashboards and navigation. Poppins covers body text, form labels, table data, and metadata. The scale runs from 32px headings to 10px metadata, with every size and weight named and documented — so a developer could implement from spec without guessing.

Spacing and layout

A standardised spacing system replaced ad hoc padding and margin decisions. Consistent component spacing, section padding, and grid behaviour created predictable layouts across modules — reducing the effort of moving between different parts of the product.

07 — Components

Every state, every edge case

The hardest part of building components for an enterprise system isn't the default state — it's everything else. Empty, loading, error, disabled, focused, filled, indeterminate. Here are three in depth, followed by the rest of the library.

01File uploads

Procurement workflows involve heavy document handling, so this component covers every real state users encounter — with and without a template download option.

02Tags + status indicators

Status tags and progress rings used across approval workflows and supplier management — built on the semantic colour layer, so every state reads the same way in every module.

03Workflow builder

The most complex category: connector lines, condition builders, flow type selectors, and approval chain configurators — designed so non-technical users can set up complex approval logic without engineering support.

08 — Developer Collaboration

Built with developers, not for them

Component feasibility was aligned with the development team before and during system creation — not after. Every component was technically viable before it was finalised in Figma, and developers understood the intent behind each state and variant rather than interpreting it post-handoff.

Each component was reviewed together during handoff, with developer feedback built into the final specs. Files used consistent naming, documented states, and grouped variants that matched how developers would actually structure the code.

Having a fixed reference meant developers could concentrate on complex business logic rather than making visual decisions that should have been resolved in design. Ambiguity in handoff dropped significantly.

09 — Reflection

If given more time

I would have introduced a formal token layer — separating primitive values from semantic assignments, so theming and future brand updates could flow through the whole system without touching individual components.
To respect confidentiality agreements, visuals are recreated as simplified examples with placeholder content. I'd be happy to walk through the complete system, individual component decisions, and the handoff process during a conversation.
